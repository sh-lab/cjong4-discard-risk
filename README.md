# cjong4-discard-risk

4人打ちリーチ麻雀の公開牌配置と打牌候補から、放銃しやすさを推定する軽量な危険度評価器。

[cjong4](https://github.com/sh-lab/cjong4) が生成するマスク済みプレイヤービューを利用し、打牌候補ごとに `0..255` の危険度スコアを返します。スマートフォンとWebブラウザへの組み込みを対象とします。

現在は仕様検討段階です。このリポジトリには、推論器・学習器・学習済みモデルはまだありません。

## 目的

- 自分から見える牌配置だけを入力として、候補牌の放銃しやすさを推定する。
- 候補間だけでなく、異なる局面でも同じスコアが同程度の危険を表す共通尺度を目指す。
- モデルサイズと計算量を抑え、スマートフォンとWebブラウザで利用する。
- 牌効率や押し引きを担当するルールベースAIと組み合わせる。

推定対象は「今この牌を切ると、相手の少なくとも1人がロンできる可能性」です。放銃時の失点や将来の放銃可能性は、初期の推定対象に含めません。

## 責務分担

| 構成要素 | 責務 |
| --- | --- |
| cjong4 | ルール、合法手列挙、状態遷移、マスク済みプレイヤービュー生成 |
| cjong4-discard-risk | 合法打牌候補の危険度推定 |
| 呼び出し側のルールベースAI | 牌効率、リーチへの対応、押し引き、個性付け、最終行動選択 |

```text
マスク済みプレイヤービュー + 合法打牌候補
    -> 入力生成
    -> 危険度評価器
    -> 危険度スコア
    -> 牌効率・押し引きのルールと統合
    -> 最終行動
```

評価器は合法性判定を行わず、呼び出し側が提示した合法打牌を評価します。

## 入力仕様

受け渡し用の入力は414バイトです。C構造体を直接保存せず、各フィールドを明示的に直列化します。

| 入力 | サイズ |
| --- | ---: |
| マスク済み `locations[136]` の `discard`・`placement`・`discard_history` | 408バイト |
| 公開済み表ドラ表示牌の物理牌ID、最大5枚 | 5バイト |
| 評価対象の合法打牌の物理牌ID | 1バイト |
| 合計 | 414バイト |

### 牌配置

`cj4_player_view.locations` から `wall` 以外の3フィールドを使用します。

```c
input[tile_id * 3 + 0] = locations[tile_id].discard;
input[tile_id * 3 + 1] = locations[tile_id].placement;
input[tile_id * 3 + 2] = locations[tile_id].discard_history;
```

完全状態の牌配置は推論入力に使いません。cjong4が対象プレイヤー向けにマスクした情報を使用します。

この入力には、自分の手牌と、公開されている捨牌・副露・捨牌履歴が含まれます。相手のリーチ状態や副露数を独立した追加バイトとして渡す仕様にはせず、配置からの特徴抽出方法を今後決めます。

### ドラ表示牌

```c
input[408 + i] = dora_indicator_tile_ids[i]; /* i = 0..4 */
```

- 実際のドラ牌種ではなく、公開済みの表ドラ表示牌の物理牌IDを渡します。
- 有効な物理牌IDは `0..135` です。
- 未公開・存在しない枠は `CJ4_TILE_ID_INVALID`、すなわち `255` とします。
- 裏ドラ表示牌は入力しません。
- 表示牌を入力することで、`wall` を除いても表示牌として公開されている牌を識別できます。
- 実際のドラ牌種が必要な場合は、前処理で表示牌から変換できます。

5枠への格納順序など、入力の正規化規則は今後確定します。

### 打牌候補

```c
input[413] = candidate_tile_id;
```

候補IDは `0..135` の物理牌IDです。同じ局面で同じ牌種を切る場合は、同じ危険度を返すことを目指します。内部で牌種へ変換する案を検討しています。

### 受け渡し形式とモデル特徴量

414バイトは入力の受け渡し形式であり、NNの入力ノード数を414に固定する意味ではありません。

牌ID、プレイヤー番号、ビットフラグ、未使用値を単純な連続数値として扱わず、フィールドを解読して特徴量へ変換する方針です。具体的な特徴量と次元数は未確定です。

## 出力仕様

```c
uint8_t danger;
```

| 値 | 意味 |
| --- | --- |
| 0 | 最も危険度が低い |
| 255 | 最も危険度が高い |

- 同点を許容します。
- モデルの出力が0でも、放銃しないことを保証しません。
- 出力は危険度スコアであり、値をそのまま放銃確率の百分率として解釈しません。
- 異なる局面でも、同じスコアが同程度の危険を表すことを目指します。
- スコアと危険度の対応、尺度の補正方法、1バイトへの変換方法は今後確定します。

順位学習だけでなく、局面をまたいだ尺度の一致を評価する必要があります。

## 呼び出し側での評価削減

- 同じ局面の同じ牌種は1回だけ評価し、結果を共有します。
- ルールで相手全員に対して放銃しないと確定できる候補は、モデルを呼ばず危険度0として扱えます。
- 特定の相手の現物であることだけでは、相手全員に対する安全判定にはなりません。
- 筋など、推測による安全性だけを根拠に確定安全として扱いません。

キャッシュは局面にひも付け、状態が変わった場合は再評価します。

## モデルと実装の検討案

以下は初期候補であり、確定仕様ではありません。

- 通常の小型NNを基準モデルとする。
- 中間層は `256 -> 128 -> 64` の3層、隠れ層の活性化はReLUを第一候補とする。
- 学習はfloat32、配布はINT8の重み・活性値とINT32積和を検討する。
- 共通のC推論器を、スマートフォンではネイティブ、WebではWebAssemblyとして利用する。
- 推論中の動的メモリ確保を避ける。
- まず全牌種共通の1モデルを基準とする。

局面処理と候補処理を分けて計算を共有する案もありますが、呼び出し側で削減した後の評価回数と実測速度を見て判断します。一括評価APIや局面特徴のキャッシュは必須要件にしません。

過去に検討した「1・9」「2・8」「3〜7」「風牌」「三元牌」の5モデル分割、論理ゲート方式、固定された旧トポロジーは、現在の確定仕様には含めません。

Playdateへの対応は当面の対象外です。

## 学習と検証

教師データの生成方式と損失関数は未確定です。ルールによる危険ランクの模倣と、対局局面で各候補が実際にロン可能かを教師にする方式などを比較検討します。

主な検証項目は次のとおりです。

- スコア帯ごとの実際のロン可能率と、局面をまたぐ尺度の一致。
- 危険な候補を低い危険度に見積もる頻度。
- リーチ有無、副露数、局の進行段階、牌種分類ごとの精度。
- 同一牌種の物理牌IDの違いに対する出力の安定性。
- float32版と量子化版の精度・尺度の差。
- Cネイティブ版とWebAssembly版の整数推論の一致。
- モデルサイズ、作業メモリ、特徴量生成を含む1手あたりの処理時間。

学習・検証・最終評価のデータは対局単位で分離します。危険局面を増やすために標本の割合を変える場合は、実利用時の分布で尺度を検証する必要があります。
